# Chat（聊天服务）

> 端口：10010 | 服务名：chat | 依赖：Config、Util、DTO

---

## 1. 这个模块是干什么的

Chat 是整个 SeekFood 平台的**实时沟通通道**。一个外卖订单从下单到送达，中间可能有很多事情需要沟通 —— 用户想问"能不能多加辣"、商家要通知"骑手已取餐"、骑手要说"我到楼下了"。Chat 模块就是为这三方（用户、商家、骑手）提供一个**绑在订单上的聊天室**，让他们能在一个地方说话。

这个模块要做的事情其实就三件：

第一，**管理聊天室**。每个订单在派单成功后，会自动生成一个聊天室，三方都能进来。订单完成后，聊天室关闭。

第二，**收发消息**。支持文字消息和图片消息，消息发出去后通过 WebSocket 实时推送给聊天室里的其他人，不用刷新页面就能看到。

第三，**消息历史**。所有聊天记录都存起来，用户可以随时翻看历史消息，也支持撤回。

---

## 2. WebSocket 是怎么工作的（长连接 vs 短连接）

开始之前，先理解一个很关键的概念：**你平时打开网页、发帖、查数据，用的是 HTTP（短连接），每次请求完就断开。但聊天不一样，你不能每秒钟都发一个 HTTP 请求去问"有新消息吗？"—— 这样服务器会被打爆。**

WebSocket 就是解决这个问题的。它做的事情很简单：**客户端和服务器之间建立一条"管道"，这条管道一直不关，谁想发消息就顺着管道扔过去，对方立刻就能收到。** 这就是"长连接"和"短连接"的区别：

- 短连接（HTTP）：每次说话都得先敲门，说完就关门，下次说再敲。效率低，浪费资源。
- 长连接（WebSocket）：一次敲门，门就一直开着，随时说话，随时听到。

**那 Chat 模块具体是怎么用 WebSocket 的？**

看 `ChatInformServer` 这个类，它就是 WebSocket 的"接线员"。当一个用户（或商家、骑手）打开聊天页面时，前端会发一个 WebSocket 连接请求，URL 里带上 `roomId`（聊天室 ID），请求头里带上 JWT Token（身份凭证）。

接线员收到连接后，做四件事：

1. 从 URL 里取出 `roomId`，验证这个 ID 是否合法。
2. 从请求头里取出 Token，解析出你的身份 ID，同时检查你有没有"操作太频繁"（冷却机制，防止有人写脚本刷消息）。
3. 检查你是不是这个聊天室的合法成员 —— 你一个路人甲当然不能进别人的聊天室。
4. 检查通过后，把你的 WebSocket 会话（session）存到一个 `ConcurrentHashMap` 里，结构是 `{roomId -> {userId -> session}}`。

这样，当有人发消息时，只需要找到对应的 `roomId`，然后遍历里面的所有 session，挨个推送消息就行了。**不需要查数据库，不需要经过 HTTP，纯内存操作，非常快。**

## 3. 聊天室是怎么自动创建的

聊天室不是手动创建的，它跟订单的生命周期绑定在一起。整个过程由 **MQ（消息队列）** 驱动，分成三步：

**第一步：订单服务发出"创建聊天室"的消息。** 当订单状态变为"派单成功"（即用户、商家、骑手三方都确定了），Order 服务就向 RabbitMQ 发一条消息，内容是一个 `ChatRoomDTO`，里面包含了订单 ID、用户 ID、商家 ID、骑手 ID。

**第二步：Chat 模块的消费者收到消息，创建聊天室。** `ChatRoomInitConsumer` 监听着这个队列，收到消息后，它用 Redis 的自增计数器生成一个全局唯一的 `roomId`，然后往 `chat_room` 表里插入一条记录。这条记录包含了三方 ID 和订单 ID，还有一个 `ending_time` 字段，表示这个聊天室的默认存活时间（比如订单完成后 7 天自动过期）。

**第三步：订单完成后，标记聊天室关闭。** 当订单完成时，Order 服务又发一条消息到另一个队列。`ChatRoomCompleteConsumer` 收到后，把对应聊天室的 `is_complete` 字段设为 `true`，聊天室就关闭了，不再接受新消息。

**为什么用 MQ 而不是直接调接口？** 因为 Order 服务不需要关心 Chat 服务是否在线、创建是否成功。如果 Order 直接调 Chat 的接口，万一 Chat 服务挂了，订单创建也会失败。用 MQ 的话，消息丢到队列里就完事了，Chat 服务启动后自然会消费。这种"异步解耦"是微服务架构里最常见的模式。

## 4. 消息怎么收发

消息的完整流程是这样的：

**发送：**

1. 用户在聊天页面输入文字（或上传图片），前端调用 `POST /chat/record` 接口，带上文字内容、图片文件、聊天室 ID。
2. `ChatRecordService` 收到请求后，先做参数校验，再检查这个用户是不是聊天室的合法成员。
3. 如果有图片，先把图片存到服务器磁盘上，然后通过 RabbitMQ 的**死信队列**设置一个延时删除任务 —— 比如 30 分钟后自动删除。这个设计是为了防止用户撤回消息后图片变成垃圾文件没人清理。
4. 用 Redis 自增计数器生成消息 ID，把消息写入 `chat_record` 表。
5. **最关键的一步**：往 RabbitMQ 发一条通知消息，内容是"聊天室 XXX 有新消息了"。

**接收：**

6. `ChatRoomInformConsumer` 监听到这条通知，拿到 `roomId`，调用 `ChatInformServer` 的 `broadcastRoomId` 方法。
7. `broadcastRoomId` 从内存里的 `Session_Map` 中找到这个聊天室的所有 WebSocket 会话，逐个发送 `"有新的消息到达"` 的推送。
8. 前端收到推送后，调用 `GET /chat/record/list` 接口拉取最新消息，渲染到聊天界面上。

**为什么要先写数据库，再推通知，而不是直接推消息内容？** 因为 WebSocket 推送是不可靠的 —— 用户可能刚好断网了，消息推过去会丢。如果把消息内容先存到数据库，再通知前端"来拉取"，前端主动来拉数据，这样消息绝对不会丢。而且如果前端已经在拉取过程中，它可以直接拿到完整消息，不用担心推送和拉取的数据不一致。

**撤回功能**也很简单：用户调用 `PUT /chat/record/withdraw`，传消息 ID，后端检查是不是本人发的、有没有超过撤回时限（比如 2 分钟），然后更新 `is_withdraw = true`。前端看到这条消息时，显示"已撤回"而不是原始内容。

## 5. 亮点和坑

**亮点：**

- **WebSocket 会话管理用 ConcurrentHashMap + 双层 Map**。外层 key 是聊天室 ID，内层 key 是用户 ID。这样同一个聊天室里有几个用户就一目了然，广播消息时不需要遍历所有会话，只遍历目标聊天室的。

- **MQ 异步解耦**。聊天室创建、订单完成通知、文件延时删除，全部通过 MQ 完成。各个服务之间不直接调用，Chat 挂了不会影响 Order，Order 挂了也不会影响 Chat。

- **Redis 分布式 ID 生成**。用 Redis 的 `INCR` 命令生成全局唯一的聊天室 ID 和消息 ID，比数据库自增更灵活，也避免了分库分表时的 ID 冲突。

- **死信队列做延时删除**。用户上传图片后，如果撤回消息，图片需要被删除。但如果直接删，万一用户快速撤回又快速恢复（虽然目前不支持恢复），图片就没了。所以用 RabbitMQ 的死信队列设置一个延时（比如 30 分钟），到时间后再真正删除。同时还有一个定时任务 `OldFileClearScheduled`，通过 Redis Stream 处理那些第一次删除失败的文件，保证磁盘空间不会无限增长。

**坑：**

- **WebSocket 连接的权限校验要特别注意**。连接建立的时候必须校验 Token 和聊天室成员关系，不能只在前端校验—— 前端校验等于没校验，因为任何人都可以绕过前端直接发 WebSocket 请求。

- **ConcurrentHashMap 是内存存储，服务重启就没了**。如果 Chat 服务重启，所有 WebSocket 连接都会断开，内存里的 `Session_Map` 也清空了。但这不是什么大问题，因为前端检测到断开会自动重连，重连后 session 重新注册到 `Session_Map` 里。

- **冷却机制用的是 Redis 的 TTL**。每个用户发消息、查记录都有冷却时间，防止有人刷接口。但如果 Redis 挂了，冷却检查就会失败。好在这个项目的冷却配置允许在 Nacos 里动态调整，可以根据实际情况随时调松或调紧。

## 6. 快速启动

**前置条件：**
- MySQL 8.0+（执行 `src/main/resources/MysqlCreate.sql` 建库建表）
- Redis 7.0+
- RabbitMQ 3.9+
- Nacos 2.0+（需要配置好 namespace、group 和相关的配置文件）

**启动步骤：**

1. 确保 Config、Util、DTO 三个公共模块已经编译安装到本地 Maven 仓库。
2. 确保 Nacos 上已经配置好了 `chat-self-dev.yaml`、`mq-name-bind-dev.yaml`、`common-param-rules-dev.yaml` 等配置文件。
3. 启动 Chat 服务的主类 `ChatApplication.java`。
4. 启动后，服务会注册到 Nacos，端口为 10010。

**验证：**
- 启动其他服务（Order、User、Merchant、Rider 等），触发一个订单的派单流程，检查 `chat_room` 表是否自动创建了聊天室记录。
- 用 Postman 或浏览器 WebSocket 客户端连接 `ws://localhost:10010/chat/room/websocket?roomId=xxx`，检查是否能连接成功。
- 发送一条消息，检查 `chat_record` 表是否有记录，同时 WebSocket 客户端是否收到推送通知。
