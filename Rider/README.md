# Rider（骑手服务）

> 端口 **10008** | 服务名 **rider** | 数据库 **seek_food_rider**

---

## 1. 这个模块是干什么的？

Rider 服务负责整个 SeekFood 平台里**骑手**相关的所有操作。骑手可以通过这个服务注册账号、登录、管理自己的资料（头像、密码等），以及后续的接单配送和收入管理。

这个服务包含三个子模块：**注册**（Register）、**登录**（Login）、**骑手管理**（Rider）。它们各自有独立的 Controller、Service 和 Mapper，职责分离得很清楚。

---

## 2. 骑手从注册到接单的完整流程

让我们跟着一个新骑手走一遍完整流程，看看每一步背后发生了什么：

### 第一步：获取验证码

骑手在 App 上输入手机号，点击"获取验证码"。服务端先校验手机号格式，然后生成一个 6 位随机数字验证码，存入 Redis 并设置过期时间（比如 5 分钟）。验证码通过短信通道发给骑手——不过这个服务本身不负责发短信，只负责生成和校验。

### 第二步：注册

骑手填写姓名、身份证号、手机号、密码、性别，输入验证码，点击注册。服务端会做这些事：

- **先校验所有参数**：姓名格式、身份证号格式、手机号、密码强度、性别合法性，统统过一遍。
- **再校验验证码**：从 Redis 里取出之前存的验证码比对，比完就删掉，防止重复使用。
- **然后检查冷却期**：同一个手机号在冷却期内不能重复注册，防止恶意刷号。
- **接着生成骑手 ID**：用 Redis 计数器生成一个全局唯一的骑手 ID。
- **写入数据库**：插入 `rider` 表。
- **发 MQ 消息**：通知 Fund（资金）服务为新骑手创建收入账户。这一步是异步的，注册不需要等资金账户创建完成。
- **最后清理缓存**：删除可能存在的空缓存（防止之前有人用猜测 ID 的方式创建了空缓存标记）。

### 第三步：登录

注册成功后，骑手可以用两种方式登录：

**验证码登录**：输入手机号 -> 获取验证码 -> 输入验证码 -> 登录。服务端校验验证码后，生成 JWT Token，同时写入 Redis（用于多设备管理和 Token 过期控制）和 Cookie（HttpOnly，防止 XSS 攻击）。

**密码登录**：输入手机号 + 密码 -> 登录。不过密码登录多了个冷却期限制：输错密码后一段时间内不能重试，防止暴力破解。

登录成功后返回骑手的基本信息，后续请求都会带上 JWT Token，网关解析后把骑手 ID 写入 `TokenIdContext`（ThreadLocal），服务端通过这个 ID 知道"当前是谁在操作"。

### 第四步：资料管理

骑手可以查看自己的信息、上传头像、修改密码、甚至注销账号。

- **查看信息**：走 Caffeine -> Redis -> MySQL 三级缓存。
- **上传头像**：先校验文件格式和大小，保存到指定目录，然后更新数据库中的头像地址。旧头像文件通过 MQ 异步删除，而不是同步删除，避免阻塞用户请求。
- **修改密码**：需要短信验证码，校验通过后更新密码。
- **注销账号**：需要短信验证码，通过后逻辑删除（`is_delete = true`），同时发 MQ 删除头像文件和资金账户。

### 第五步：接单配送

骑手登录后，订单服务会推送可接的订单。骑手在订单服务那边完成接单、取餐、配送等操作，这些逻辑不在 Rider 服务里，Rider 服务只负责骑手的身份认证和资料管理。

## 3. 配送收入怎么算？

收入的详细计算在 Fund（资金）服务里，但 Rider 服务做了两件关键的事：

**注册时创建资金账户。** 骑手注册成功后，Rider 服务通过 MQ 发一条消息给 Fund 服务，告诉它"新来了一个骑手，ID 是 xxx，请帮他开个账户"。Fund 服务收到消息后就创建对应的资金账户。

**注销时删除资金账户。** 骑手注销账号时，Rider 服务同样发 MQ 消息给 Fund 服务，让它清理对应的资金账户。

Rider 服务本身不存收入数据，它只负责把"骑手来了"和"骑手走了"这两个事件通知给 Fund 服务。后续每一笔配送收入，都是订单服务 -> Fund 服务的链路，与 Rider 服务无关。

## 4. 亮点和坑

**亮点：**

- **JWT + Cookie 双重认证**：Token 不仅放在响应头里，还写入 HttpOnly Cookie，浏览器环境下自动携带，同时防止 JS 读取，兼顾方便和安全。
- **多设备 Token 管理**：用 Redis 的 ZSet 存储每个用户的 Token 列表，自动淘汰过期 Token，支持"一个账号多个设备同时登录"。
- **Caffeine 双缓存**：骑手信息（`RiderCaffeine`）和骑手手机号（`RiderPhoneCaffeine`）各有一套独立缓存。手机号缓存是出于一个巧妙的设计：修改密码、注销等操作需要手机号，但不想每次都查数据库，所以就多了一层手机号缓存。
- **注册时自动清理空缓存**：注册完成后，如果之前有人用该 ID 查询过（产生了空缓存标记），注册逻辑会主动删除这个空缓存。不然新注册的骑手查不到自己的信息，那就尴尬了。
- **文件异步删除 + 定时清理兜底**：跟 Meal 服务一样，头像旧文件通过 MQ 异步删除，删不掉就写 Redis Stream，由定时任务每 5 秒重试一次。这是项目里统一的文件清理策略。
- **冷却期无处不在**：登录密码重试、注册、修改密码、修改头像、注销，每个敏感操作都有冷却期，有效防止暴力攻击。

**坑：**

- 骑手注销后，数据库里只是逻辑删除（`is_delete = true`），但 MQ 发出去删除资金账户和文件的消息如果消费失败，可能会留下孤儿数据。虽然有定时任务兜底，但文件清理和资金账户清理是两条独立的链路。
- JWT Token 的刷新机制依赖 Redis 的 ZSet 存储，如果 Redis 挂了，刷新 Token 会失败，但旧的 Token 还能用（因为 JWT 本身还未过期）。

## 5. 快速启动

### 环境要求

- JDK 21+
- Maven 3.9+
- MySQL（需要先执行 `src/main/resources/MysqlCreate.sql` 建库建表）
- Redis（验证码、冷却期、缓存、Token 管理、ID 计数器）
- RabbitMQ（文件删除、资金账户创建/删除）
- Nacos（服务注册发现 + 配置管理）

### 启动步骤

1. 建库：执行 `MysqlCreate.sql`。
2. 确认 Nacos 中已配置好 `COMMON_GROUP`、`MQ_GROUP`、`SEEK_FOOD_GROUP` 的相关配置文件（特别是 JWT 密钥配置）。
3. 启动 Redis 和 RabbitMQ。
4. 运行 `RiderApplication.java` 主类，端口 10008。

### 核心接口一览

| 接口 | 方法 | 说明 |
|------|------|------|
| `/register/getOpt` | GET | 获取注册验证码 |
| `/register` | POST | 注册骑手 |
| `/login/getOpt` | GET | 获取登录验证码 |
| `/login` | GET | 验证码登录 |
| `/login/password` | GET | 密码登录 |
| `/login/refresh` | GET | 刷新 Token |
| `/rider/getDetail` | GET | 查看骑手信息（走缓存） |
| `/rider/getSelf` | GET | 查看自己的信息 |
| `/rider/updatePersonImage` | PUT | 修改头像 |
| `/rider/getUpdatePasswordOpt` | GET | 获取改密验证码 |
| `/rider/updatePassword` | PUT | 修改密码 |
| `/rider/getDeleteOpt` | GET | 获取注销验证码 |
| `/rider/delete` | DELETE | 注销账号 |

### 依赖关系

本模块依赖 **Config**（Nacos 配置）、**Util**（工具类：JWT、Redis、MQ、文件、验证码、ID 生成等）、**DTO**（数据传输对象）三个公共模块，不直接依赖其他业务模块。
