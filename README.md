## 这个项目是干什么的？

简单说，这就是一个**外卖平台的后端**。你可以把它想象成美团或饿了么的"骨架"——虽然没有前端页面，但背后支撑整个业务运转的所有逻辑都在这里：

- 用户可以注册、登录、浏览菜品、下单、支付、评价
- 商家可以开店、上架菜品、接单、做菜、赚钱
- 骑手可以接单、取餐、配送、拿到配送费
- 管理员可以管理平台、查看数据

**这个项目用了哪些技术？** 说出来你可能不信，它几乎把 Spring Cloud 微服务全家桶都用上了：Nacos（注册中心）、Sentinel（限流）、Seata（分布式事务）、RabbitMQ（消息队列）、Redis（缓存）、Elasticsearch（搜索引擎）、SkyWalking（链路追踪）…… 这些名字一开始你可能觉得陌生，但看完这篇文档，你会知道它们各自在系统中扮演什么角色。

## 在开始看代码之前，先理解几个核心概念

### 1. 什么是"微服务"？为什么不用一个大的 Spring Boot 项目？

想象一下，如果你把用户、订单、商家、支付、配送所有功能都塞在一个项目里会怎样？

- 改一行用户相关的代码，整个项目要重新打包部署
- 订单模块出 bug 导致内存泄漏，整个系统都崩了
- 100 个人同时开发，代码冲突让你怀疑人生

**微服务的思想就是"分而治之"**：把一个大系统拆成很多小服务，每个服务只干一件事，服务之间通过网络通信。这个项目拆成了 18 个模块，但别被这个数字吓到——它们很多是辅助模块，真正核心的业务服务就 10 来个。

### 2. 服务之间怎么通信？

这是微服务最核心的问题。这个项目用了两种方式：

- **同步调用**（Feign）：就像打电话，A 服务直接调用 B 服务的接口，等 B 返回结果后再继续。比如下单时要先查菜品信息，就必须等菜品服务返回。
- **异步消息**（RabbitMQ）：就像发短信，A 服务把消息丢到消息队列里就不管了，B 服务什么时候处理都行。比如下单后通知商家，不需要用户等着商家确认。

**什么时候用同步，什么时候用异步？** 一个简单的判断标准：如果调用方**必须拿到结果才能继续**，就用同步；如果只是**通知一下、不着急**，就用异步。

### 3. 用户登录后，怎么知道每个请求是谁发的？

这个问题在微服务里特别麻烦。用户登录后，网关给他发了一个 Token（你可以理解成一张"临时身份证"），后续所有请求都带着这个 Token。但问题是，网关验证通过后，后面的订单服务、支付服务也需要知道"是谁在操作"。

这个项目的做法是：**网关验证 Token 后，把用户 ID 塞到请求头里，后面的服务直接从请求头里取**。这样每个服务都不用重复验证 Token，只需要信任网关传过来的 ID。

## 整体架构：一个请求进来后，经历了什么？

```
用户打开 App → 请求到达网关 → 网关验证身份 → 转发给具体的业务服务
                                              ↓
                              业务服务处理逻辑 → 需要查数据？→ 先查本地缓存 → 没有再查 Redis → 再没有查数据库
                                              ↓
                              如果需要调用其他服务 → 通过 Feign 同步调用（急事）
                                              → 或者发 MQ 消息异步处理（不急的事）
                                              ↓
                              处理完毕 → 返回结果给网关 → 网关返回给用户
```

下面我用一个**真实的点餐流程**来演示：

```
用户下单：
  ① 请求到达网关 → 网关从 Cookie 中取出 Token，验证这是谁
  ② 网关把用户 ID 塞到请求头，转发给订单服务
  ③ 订单服务拿到用户 ID，先加一把分布式锁（防止用户重复点单）
  ④ 订单服务调用菜品服务 → 查菜品是否存在、价格对不对
  ⑤ 订单服务调用商家服务 → 计算配送距离和费用
  ⑥ 订单服务调用优惠券服务 → 检查优惠券能否使用
  ⑦ 一切都校验通过 → 订单服务把订单写入数据库
  ⑧ 订单服务发 MQ 消息给资金服务 → "这个订单要扣钱了"
  ⑨ 订单服务返回"下单成功"给用户
```

**注意看第 ⑧ 步**：为什么扣钱不发同步请求，而是发 MQ 消息？因为扣钱不是用户下单后必须立刻完成的事——用户只需要知道"下单成功"，至于钱什么时候扣，可以稍微延迟一点。这就是异步的优势：**让用户尽快得到响应，后台慢慢处理**。

## 项目里有哪些模块？各自负责什么？

### 一、基础模块（不处理业务，但所有业务模块都依赖它们）

| 模块 | 干什么的 | 为什么要有它 |
|------|---------|-------------|
| **Gateway**（网关） | 所有请求的入口，负责验证身份、转发请求 | 如果没有网关，每个服务都要自己验证 Token，代码重复且不安全 |
| **Config**（配置中心） | 管理所有服务的配置，比如 JWT 密钥、Redis Key、MQ 交换机名 | 配置统一管理，改一个地方所有服务生效，不用改代码 |
| **Util**（工具库） | 封装了 JWT 生成、Redis 操作、MQ 发送、缓存等通用逻辑 | 每个服务都要用这些功能，抽出来避免重复写 |
| **DTO**（数据对象） | 定义服务之间传输的数据结构 | 服务间通信需要统一的数据格式，不然各说各话 |
| **ErrorConsumer**（异常处理） | 监听 MQ 中处理失败的消息，记录日志 | 消息队列里的消息处理失败了不能丢了，需要有人兜底 |

### 二、业务模块（真正处理外卖业务的）

| 模块 | 端口 | 干了什么 |
|------|------|---------|
| **User** | 10001 | 用户注册登录、修改资料、上传头像 |
| **Merchant** | 10002 | 商家注册开店、管理菜品、控制营业状态 |
| **Employee** | 10003 | 商家员工管理（一个商家可以有多个员工） |
| **Meal** | 10004 | 菜品管理：上架、下架、修改、查询 |
| **Fund** | 10005 | 资金管理：充值、提现、支付、退款流水 |
| **Voucher** | 10006 | 优惠券：商家发券、用户领券、下单用券 |
| **Promotion** | 10007 | 营销活动：登录即得券、限时抢券 |
| **Rider** | 10008 | 骑手注册、接单配送、收入管理 |
| **Order** | 10009 | ★ 核心模块：订单的完整生命周期 |
| **Chat** | 10010 | 实时聊天：用户-商家-骑手三方沟通 |
| **Comment** | 10011 | 评论系统：一级评论 + 二级回复 + 点赞 |
| **Interaction** | 10012 | 互动功能：收藏商家、点赞内容 |
| **Admin** | 10013 | 管理后台：管理员登录、处理建议、查看统计 |

> **端口为什么从 10001 开始？** 10000 是网关，10001 开始是业务服务，这样一眼就能看出端口对应哪个服务。而且留了足够的扩展空间（10014-10099 可以给未来新服务）。

## 核心设计：每个服务内部长什么样？

虽然每个服务功能不同，但内部结构几乎一样。这是有意为之——**统一的结构让新人能快速上手任何模块**：

```
每个业务服务内部都分为这几层：
┌─────────────────────────────────────┐
│  Controller 层（接收请求）            │  ← 只负责接收参数、调用 Service、返回结果
├─────────────────────────────────────┤
│  Service 层（处理业务逻辑）           │  ← 核心逻辑都在这里，协调各个组件
├─────────────────────────────────────┤
│  Mapper 层（操作数据库）              │  ← 只负责写 SQL，不处理业务逻辑
├─────────────────────────────────────┤
│  Caffeine 缓存（本地内存缓存）         │  ← 热点数据直接放内存，速度最快
├─────────────────────────────────────┤
│  Consumer（MQ 消费者）               │  ← 接收其他服务发来的消息
├─────────────────────────────────────┤
│  MQBind（MQ 绑定配置）               │  ← 声明这个服务用哪些交换机、队列
├─────────────────────────────────────┤
│  Feign（调用其他服务）                │  ← 需要调其他服务时，在这里声明接口
└─────────────────────────────────────┘
```

**为什么每个服务都要有 Caffeine 缓存？** 因为 Redis 虽然快，但毕竟要走网络。对于一些经常查询、很少变化的数据（比如用户基本信息），直接放在服务的内存里，查询速度是 Redis 的几十倍。这就是"二级缓存"的设计思路：**先查本地内存（Caffeine），没有再查 Redis，没有再查数据库**。

## 最核心的流程：一个订单的一生

这是整个项目最复杂、也最能体现设计思想的部分。我建议你仔细看：

```
订单状态变化：
创建 → 商家确认 → 商家制作 → 骑手取餐 → 骑手配送 → 用户确认收货 → 完成
  ↓        ↓                                         ↓
 可取消   可拒绝                                     可退款
```

### 下单流程（最复杂的入口）

```
用户提交下单请求
  ↓
网关验证 Token，把用户 ID 放到请求头
  ↓
订单服务收到请求：
  ├→ 加分布式锁（同一用户同一时间只能有一个下单操作）
  ├→ 调用菜品服务：这个菜还存在吗？价格对吗？
  ├→ 调用商家服务：这个商家营业吗？配送距离多远？配送费多少？
  ├→ 调用优惠券服务：这张券能用吗？能减多少钱？
  ├→ 计算总价 = 菜品价格 × 数量 + 配送费 - 优惠券抵扣
  ├→ 锁定优惠券（防止重复使用）
  ├→ 把订单写入数据库
  ├→ 发 MQ 消息给资金服务 → "扣钱"
  └→ 释放分布式锁，返回"下单成功"
```

**为什么要加分布式锁？** 想象一下，如果用户在网速慢的时候狂点"下单"按钮，没有锁的话可能会创建多个完全一样的订单。分布式锁保证同一时刻只有一个请求在处理。

**为什么用 Seata 分布式事务？** 下单这个操作涉及多个服务：订单服务写订单、资金服务扣钱、优惠券服务锁定券。如果其中一步失败了，前面成功的步骤必须回滚。Seata 就是干这个的——保证跨服务的操作要么全部成功，要么全部回滚。

### 商家接单后的流程

```
商家确认接单
  ↓
订单状态变为"商家已确认"
  ↓
ES 同步：把订单信息写入 Elasticsearch → 骑手端可以搜索到
  ↓
商家开始制作
  ↓
制作完成 → 订单状态变为"等待骑手取餐"
  ↓
同时发 MQ 消息给资金服务 → 把菜品收入打给商家
同时发 MQ 消息给商家服务 → 增加商家订单数
同时发 MQ 消息给菜品服务 → 增加菜品销量
```

**注意这里的设计**：商家做完菜后，系统同时干了三件事——打钱、统计订单数、统计销量。但三件事都是通过 MQ 异步处理的，不会阻塞用户。这就是"事件驱动"的设计思想：**一个动作触发多个事件，各干各的，互不阻塞**。

### 骑手配送流程

```
骑手在 App 里搜索可接订单
  ↓
订单服务从 Elasticsearch 查询（ES 支持地理位置搜索，能按距离排序）
  ↓
骑手接单 → 订单状态变为"已接单"
  ↓
同时发 MQ 消息给聊天服务 → 自动创建"用户-商家-骑手"三方聊天室
  ↓
骑手到店取餐 → 确认已取餐
  ↓
骑手配送到目的地 → 确认已送达
  ↓
发 MQ 消息给资金服务 → 配送费打给骑手
  ↓
用户确认收货 → 订单完成
  ↓
发 MQ 消息给用户服务 → 增加用户下单次数
发 MQ 消息给聊天服务 → 关闭聊天室
```

### 退款怎么处理？

```
用户申请退款 / 商家拒绝订单
  ↓
订单服务检查：这个订单当前状态允许退款吗？
  ↓
更新订单状态为"已退款"
  ↓
发 MQ 消息给资金服务 → "这个订单要退钱"
  ↓
资金服务收到消息 → 把钱从商家账户扣回，还给用户
```

## 这个项目用了哪些"高级"技术？为什么用它们？

### 1. RabbitMQ（消息队列）—— 让系统"异步"起来

**没有 MQ 时**：用户下单 → 系统要扣钱、发通知、统计销量……全部做完才返回"下单成功"，用户干等。

**有 MQ 后**：用户下单 → 系统只做"必须立刻完成"的事（写订单），然后把"可以慢慢做的事"（扣钱、发通知）丢到队列里，立刻返回"下单成功"。

**MQ 的另一个妙用：死信队列**。这个项目有一个很聪明的设计：订单创建后，会发一条"延时消息"给资金服务，说"如果 30 分钟后这个订单还没支付，自动退款"。这就是通过 RabbitMQ 的 TTL（消息存活时间）+ 死信队列实现的。

### 2. Redis（缓存）—— 不止是缓存

这个项目里 Redis 干了至少 5 件事：

- **缓存**：热点数据放 Redis，减少数据库压力
- **分布式锁**：通过 Redisson 实现，防止并发问题
- **冷却期**：防止用户频繁操作（比如 1 分钟内只能发一次验证码）
- **BitMap**：用位图存储"是否收藏""是否点赞"，节省内存
- **计数器**：生成分布式唯一 ID（订单号、流水号）

### 3. Caffeine（本地缓存）—— 比 Redis 还快

Redis 虽然快，但毕竟要走网络（一次 Redis 查询大概 1ms）。Caffeine 是直接放在 JVM 内存里的，查询速度是微秒级别。

这个项目的缓存策略是：**Caffeine（本地内存）→ Redis（分布式缓存）→ MySQL（数据库）**。查数据时先查 Caffeine，查不到再查 Redis，再查不到才查数据库。

**但有个问题**：如果 A 服务更新了数据，B 服务的 Caffeine 缓存还是旧的怎么办？这个项目用了"更新即删除"的策略：只要数据更新了，就把对应的缓存删掉，下次查询时自然会重新加载。

### 4. Seata（分布式事务）—— 跨服务数据一致性

下单时，订单服务要写订单、资金服务要扣钱、优惠券服务要锁定券。如果资金服务扣钱失败了，订单已经写了怎么办？

Seata 的 AT 模式会在每个服务操作数据库时记录"回滚日志"（Undo Log），如果任何一步失败，就用回滚日志把数据恢复回去。

### 5. Sentinel（限流熔断）—— 保护系统不被冲垮

假设有人恶意刷接口，一秒发 10000 个请求，系统会怎样？Sentinel 可以：
- **限流**：超过配置的 QPS（每秒请求数），直接拒绝
- **熔断**：如果某个服务一直出错，暂时不再调用它，给它恢复时间
- **降级**：熔断后返回一个兜底结果，而不是让用户看到错误

### 6. Elasticsearch（搜索引擎）—— 让搜索变快

MySQL 也能搜索，但数据量大时非常慢。ES 是专门为搜索设计的，支持：
- 地理位置搜索（找附近的商家、找附近的订单）
- 模糊搜索（商家名称部分匹配）
- 多条件组合查询（距离 + 价格 + 评分）

这个项目在哪些地方用了 ES？主要是骑手搜索订单（按地理位置找附近的待配送订单）和商家搜索。

## 安全设计：系统是怎么保护自己的？

### 1. 网关层面

- **Token 放在 HttpOnly Cookie 里**：前端 JavaScript 无法读取，防止 XSS 攻击偷走 Token
- **多角色密钥隔离**：用户、商家、骑手、管理员用不同的密钥签发 Token，即使某个密钥泄露，不影响其他角色
- **IP/ID 黑名单**：同一个 IP 或用户短时间内请求太多，自动封禁

### 2. 服务层面

- **冷却期机制**：重要操作（发验证码、下单、退款）都有冷却期，防止用户短时间内重复操作
- **分布式锁**：关键操作（下单）加锁，防止并发问题
- **参数校验**：所有入参都经过校验，防止非法数据入库

### 3. 数据层面

- **逻辑删除**：用户注销、订单取消都不是物理删除，而是标记为"已删除"，数据可追溯
- **敏感数据脱敏**：日志中不打印密码、Token 原文

## 这个项目的设计有哪些"坑"和"取舍"？

没有完美的设计，每个选择都有 trade-off。我来聊聊这个项目中的一些取舍：

### 1. 为什么用 `@RefreshScope` 但又要注意它的问题？

`@RefreshScope` 可以让配置在 Nacos 中修改后不需要重启服务就生效，非常方便。但它有一个副作用：**它会产生一个代理对象，可能和 `@Transactional` 事务注解冲突**。

这个项目中，很多 Service 类同时加了 `@RefreshScope` 和 `@Transactional`，这在某些场景下可能导致事务失效。正确的做法是：把配置读取和业务逻辑分开，只在配置读取的类上加 `@RefreshScope`。

### 2. 为什么 MQ 消费者没有做幂等校验？

**幂等**的意思是：同一条消息无论被消费多少次，结果都一样。比如扣钱操作，如果同一条消息被消费了两次，就会扣两次钱——这是绝对不允许的。

这个项目目前的 MQ 消费者（如 `TransferFundConsumer` 资金转账消费者）没有做幂等校验，如果消息因网络问题被重复投递，可能导致重复扣款。实际生产环境中应该通过"消息 ID + Redis 判重"来解决。

### 3. 为什么文件存储在本地而不是对象存储？

这个项目把用户头像、商家图片等文件直接存在本地磁盘。这在单机部署时没问题，但如果部署多个实例，实例 A 存的图片实例 B 访问不到。

生产环境应该迁移到 MinIO、阿里云 OSS 等对象存储服务，接口返回 URL 而不是本地路径。

### 4. 为什么 Feign 调用没有降级方案？

当订单服务调用菜品服务时，如果菜品服务挂了，订单服务怎么办？目前的设计是直接抛出异常，用户看到的是"系统错误"。

更好的做法是：每个 Feign 客户端都配置一个 fallback 兜底类，当下游服务不可用时，返回一个默认值或缓存数据，而不是直接报错。

### 第一步：搭环境（1-2 天）

```bash
# 你需要安装这些：
```

### 第二步：从最简单的模块开始（1-2 天）

建议的学习顺序：
1. 先看 `pom.xml`（根目录），理解项目依赖管理
2. 看 `Config` 模块，理解配置是怎么统一管理的
3. 看 `Util` 模块，理解工具类是怎么封装的

### 第三步：理解核心流程（2-3 天）

仔细跟读 `Order` 模块的 `insertOrder` 方法，用笔画出每一步的调用链。这是整个项目最复杂的方法，理解了它就理解了整个项目。

### 第四步：搭建自己的模块（3-5 天）

按照同样的结构，试试搭建一个自己的模块。比如给系统加一个"评价管理"功能。

这个项目是一个独立开发者用业余时间从零搭建的。它不完美——有 SQL 拼写错误、有被注释掉的过滤器、有没做幂等的 MQ 消费者——但**这些"不完美"恰恰是学习的价值所在**。你能看到一个真实的项目是什么样子，能看到开发者在哪些地方做了取舍，哪些地方因为时间不够留下了技术债。
