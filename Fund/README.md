# Fund 模块 -- 资金账户服务

> 端口：10005 | 服务名：fund | 依赖：Config、Util、DTO

---

## 1. 这个模块是干什么的

Fund 模块是整个 SeekFood 系统的"钱包"。每一个用户、商家、骑手在系统里都有一个资金账户，这个模块负责管理这些账户的余额，以及所有跟钱有关的操作：充值、提现、订单支付扣款、退款。

你可能会问："为什么要把资金单独拆成一个服务？" 因为钱是系统里最敏感的东西。如果资金逻辑跟订单、商品混在一起，一旦出 bug，排查起来就像在一堆电线里找短路的那个接头。拆成独立服务之后，边界清晰了：凡是跟余额变动有关的，都来找 Fund。而且独立部署意味着即使其他服务挂了，资金服务还能正常运行（反过来也一样），不会互相拖累。

这个模块对外暴露的是一组 REST API，但有意思的是，大部分"写"操作（充值到账、退款确认、账户注册等）都不是直接通过 API 调用的，而是通过消息队列异步触发的。这么做是为了削峰和解耦，我们后面会详细讲。

---

## 2. 钱是怎么流转的

### 充值链路

用户在前端发起充值请求后，系统并不是直接调用 Fund 模块，而是先在订单模块生成一笔充值订单，然后发一条消息到 RabbitMQ。Fund 模块里的 `TransferFundConsumer` 收到这条消息后，才真正开始干活：先调用 `increaseFund` 把余额加上去，再用 Redis 的 INCR 命令生成一个全局唯一的充值流水号，最后把这条充值记录写入 `fund_recharge_record` 表。整个流程是：**订单模块发起 -> MQ 投递 -> Fund 消费者处理 -> 余额变更 + 流水记录**。

为什么充值走 MQ 而不是直接调接口？因为充值通常涉及外部支付（微信、支付宝），回调时间不确定。如果同步等待，用户界面会卡住很久。异步之后，用户付完款就能立刻看到"充值已提交"，后台慢慢处理，两边都不耽误。

### 支付链路

支付也分同步和异步两步走。用户下单后，先由 `RegisterFundOrderRecordConsumer` 在 `fund_order_record` 表里插入一条"待支付"记录，这一步不扣钱，只是占个坑。同时它还会发出一条延时消息（通过 TTL 死信队列实现），意思是"如果到了截止时间订单还没被确认，就主观认为订单要么没有被支付，要么就是中间出现异常，就自动回滚"。

用户真正点"支付"时，调用的是 `FundOrderRecordService.pay()` 方法。这个方法是同步的，而且加了 `@Transactional` 事务注解：先检查订单是否过期，再调用 `decreaseFund` 扣减余额，然后标记订单为"已支付"，最后发一条消息通知优惠券模块核销券。这四步要么全成功，要么全回滚，保证不会出现"扣了钱但订单没标记"这种尴尬情况。

### 退款链路

退款的设计很巧妙，用了一个 MySQL 触发器 `auto_refund`。当 `RollbackFundConsumer` 收到退款消息后，它只做一件事：把 `fund_order_record` 表的 `is_refund` 字段改成 `true`。然后触发器自动触发，把扣掉的钱加回余额，同时往 `fund_order_refund_record` 表插入一条退款记录。为什么用触发器而不是 Java 代码？因为触发器在数据库层面执行，天然避免了并发问题——不会出现"两个线程同时退款导致重复加钱"的 bug。而且即使消费者重试投递了多次退款消息，UPDATE 语句的 WHERE 条件（`is_refund=false`）也会保证只退一次。

## 3. 为什么用"三级缓存"

Fund 模块在查询余额和流水记录时，用了三层存储：**Caffeine 本地缓存 -> Redis 分布式缓存 -> MySQL 数据库**。这不是为了炫技，每一层都有它存在的理由。

先说 Caffeine。它是跑在 JVM 进程内的缓存，速度最快（微秒级），但容量有限，而且每个服务实例各有一份。Fund 模块为每种实体都单独建了一个 Caffeine 实例：`FundCaffeine`（余额）、`FundOrderRecordCaffeine`（订单记录）、`FundOrderRefundRecordCaffeine`（退款记录）、`FundRechargeRecordCaffeine`（充值记录）、`FundWithdrawRecordCaffeine`（提现记录）。分开的好处是每种数据的过期时间和容量可以独立配置，不会互相挤占。

然后是 Redis。它比 Caffeine 慢一点（毫秒级），但所有服务实例共享同一份数据。当 Caffeine 里没有数据时，系统先去 Redis 查；Redis 也没有，才去 MySQL。查完 MySQL 后，把结果塞回 Redis 和 Caffeine，下次再查就快了。这套流程封装在 `JvmCaffeineParent` 这个父类里，所有 Caffeine 子类都继承它，所以代码很干净，不用到处写重复的"查缓存 -> 查库 -> 回填"逻辑。

为什么不用 Redis 单层缓存？因为 Redis 是网络调用，高并发下还是会成为瓶颈。Caffeine 在本地内存里，能扛住绝大多数热数据查询。比如用户反复刷新余额页面，只有第一次会穿透到 Redis，之后就一直在 Caffeine 里了。

## 4. 消息队列在这里扮演什么角色

Fund 模块不是被动等待别人调用的，它主动监听了 5 个 RabbitMQ 队列，分别对应 5 个消费者：

- **`TransferFundConsumer`**：监听充值到账消息。收到后执行余额增加 + 写入充值流水。这个操作必须是异步的，因为充值回调的时间不可控，同步等待会阻塞整个请求链路。

- **`RegisterFundOrderRecordConsumer`**：监听订单创建消息。收到后在 `fund_order_record` 表里插入一条"待支付"记录，同时发出一笔延时回滚消息。延时消息的意思是："给你 N 分钟去支付，超时没付就自动退款"。这个 N 分钟由 Nacos 配置中心动态控制，不用重启服务就能改。

- **`RollbackFundConsumer`**：监听退款确认消息。收到后调用 `ackRefund`，把订单记录标记为已退款，剩下的交给 MySQL 触发器自动处理。

- **`RegisterFundConsumer`**：监听用户注册消息。用户注册时，其他模块发一条消息过来，Fund 这边就自动创建对应的资金账户。这样 Fund 模块不用关心用户模块的注册逻辑，只管自己这一亩三分地。

- **`DeleteFundConsumer`**：监听账户删除消息。用户注销时，把资金账户标记为删除（软删除，不是物理删除，数据还留着以备审计）。

把这些操作异步化的核心原因就一个：**解耦**。Fund 模块不需要知道"订单模块什么时候创建订单"、"用户模块什么时候注册用户"，它只需要等着消息来就行。反过来也一样，充值到账后 Fund 不需要通知订单模块"我搞定了"——订单模块自己会查余额。这种单向依赖让系统架构清晰很多。

## 5. 设计中的亮点和坑

### 亮点

**冷却期机制（Cooldown）**：几乎每个写操作（充值、提现、支付、查询）都检查了冷却期。所谓冷却期，就是在 Redis 里设一个有时效的 key，同一用户在同一时间段内不能重复执行同一个操作。比如用户刚发起一笔充值，5 秒内不能再发起第二笔——防止用户手抖或脚本恶意刷接口。这个机制用 Redis 实现是因为 Redis 天然支持过期时间，比在内存里维护更可靠。

**分布式 ID 生成**：充值流水号、提现流水号、订单记录号、退款记录号，统统用 Redis 的 INCR 命令生成。INCR 是原子操作，即使有多个 Fund 实例同时调，也不会生成重复的 ID。相比雪花算法，INCR 更简单直观，而且 ID 是连续递增的，按时间排序查流水时很方便。

**软删除而非物理删除**：`deleteFund` 只是把 `is_delete` 字段设成 `true`，不会真的删数据。资金数据涉及财务审计，万一出了纠纷，得能追溯到历史记录。

**Nacos 动态配置**：缓存过期时间、冷却期时长、订单支付截止时间、回滚等待时间，这些参数全部从 Nacos 配置中心读取，而且支持热更新（`@RefreshScope`）。调参数不用重启服务，改完就生效。

### 需要注意的坑

**MySQL 触发器是双刃剑**：`auto_refund` 触发器虽然避免了并发重复退款，但也意味着退款逻辑被"藏"在了数据库里，新来的同事如果不看建表 SQL，根本不知道有这个触发器，排查问题时容易一头雾水。建议在代码注释里明确标注。

**冷却期 key 的设计**：`FundOrderRecordServiceImpl.pay()` 的冷却期 key 是 `userId + recordId` 拼接的，这样不同订单之间不会互相阻塞。但如果未来有人改了 key 的拼接规则，可能会导致冷却期失效。

**延时消息的可靠性**：`RegisterFundOrderRecordConsumer` 发送的延时回滚消息，如果 RabbitMQ 挂了，这条消息就丢了，订单会一直处于"待支付"状态。虽然提供了手动回滚的 API 做兜底，但如果用户没主动操作，垃圾数据就会一直留在表里。生产环境需要监控死信队列的积压情况。

## 6. 快速启动

### 前置条件

- JDK 21
- MySQL 8.0+（先执行 `src/main/resources/MysqlCreate.sql` 建库建表）
- Redis（用于缓存和分布式 ID）
- RabbitMQ（用于消息队列）
- Nacos（用于服务注册和配置中心）
- 已启动的 Config、Util、DTO 模块（Fund 依赖它们）

### 启动步骤

1. 在 Nacos 中创建命名空间 `123123123123`，分组 `SEEK_FOOD_GROUP`，并上传对应的配置文件（参考 `bootstrap.yml` 里的 `spring.config.import` 列表）。
2. 执行 `MysqlCreate.sql` 创建数据库和表（**注意：这个脚本会先 DROP 再 CREATE，生产环境请谨慎**）。
3. 确保 Redis 和 RabbitMQ 已启动，并且连接信息与 Nacos 配置一致。
4. 在项目根目录执行：
   ```bash
   mvn -pl Fund spring-boot:run
   ```
   或者直接在 IDE 里运行 `FundApplication.java` 的 main 方法。
5. 启动后访问 `http://localhost:10005`，如果没报错就是起来了。
