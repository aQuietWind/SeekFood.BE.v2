# 📦 Order 订单服务 — 整个系统的"心脏"

> 端口：**10009** | 服务名：`order`

---

## 这个模块是干什么的？

订单服务是整个 SeekFood 系统最核心的模块。所有其他服务——用户、商家、菜品、资金、优惠券、骑手、聊天——最终都是围绕"订单"这个中心转的。

**一个订单从生到死，要经历这些状态：**

```
用户下单 → 商家确认 → 商家制作 → 制作完成 → 骑手取餐 → 骑手配送 → 用户收货 → 完成
   ↓          ↓                                                          ↓
  可取消     可拒绝                                                     可退款
```

这个模块负责管理订单的整个生命周期：创建、查询、状态变更、退款。每一步都涉及多个服务的协作。

---

## 下单流程：整个系统最复杂的一段代码

下单是整个项目最复杂的操作，因为它涉及的服务最多。让我用自然语言描述这个流程：

### 用户提交下单请求后，发生了什么？

**第一步：身份校验与防重复**
- 从请求头中取出用户 ID（网关在之前已经放好了）
- 用这个用户 ID 作为 Key，加一把**分布式锁**
- 为什么加锁？防止用户在网速慢的时候狂点"下单"按钮，创建出多个一模一样的订单
- 如果拿不到锁（说明这个用户正在下单），直接返回"操作太频繁，请稍后再试"

**第二步：查菜品信息**
- 通过 Feign 调用菜品服务，查这个菜是否存在、价格是多少、属于哪个商家
- 如果菜不存在或已下架，直接报错

**第三步：计算配送距离和费用**
- 把用户的经纬度发给商家服务
- 商家服务用空间计算工具算出距离，返回配送费
- 为什么要把距离计算放在商家服务？因为这个计算逻辑和商家相关，放在商家服务更合理

**第四步：检查优惠券**
- 如果用户用了优惠券，调用优惠券服务检查这张券是否有效、能抵扣多少钱
- 如果券无效（被别人用了、过期了），直接报错

**第五步：计算总价**
- 总价 = 菜品价格 × 数量 + 配送费 - 优惠券抵扣
- 生成一个唯一的订单号（用 Redis 自增计数器生成）

**第六步：锁定优惠券**
- 再次调用优惠券服务，把这张券锁定到这个订单上
- 锁定后这张券就不能再被其他订单使用了

**第七步：写数据库**
- 把订单信息写入 MySQL 的 orders 表
- 清除可能存在的旧缓存（防止脏数据）

**第八步：发消息给资金服务**
- 通过 RabbitMQ 发一条消息，告诉资金服务："这个订单创建了，准备扣钱"
- 为什么用消息队列而不是直接调用？因为扣钱不需要用户干等着——用户只关心"下单成功"，钱什么时候扣是后台的事

**第九步：释放锁，返回成功**

### 用流程图表示就是：

```
用户发起下单请求
    ↓
从请求头取用户 ID → 加分布式锁（同一个用户同时只能有一个下单操作）
    ↓ 拿不到锁 → 返回"操作太频繁"
    ↓ 拿到锁
调用菜品服务 → 查菜品信息（存在吗？价格对吗？）
    ↓ 菜品不存在 → 返回"菜品不存在"
    ↓
调用商家服务 → 算配送距离和费用
    ↓
调用优惠券服务 → 检查优惠券是否可用
    ↓
计算总价 → 生成订单号 → 锁定优惠券
    ↓
写入数据库 → 清除缓存
    ↓
发消息给资金服务 → "准备扣钱了"
    ↓
释放锁 → 返回"下单成功"
```

## 订单状态变化：每一步都发生了什么？

### 1. 商家确认接单

```
商家点击"接单"
    ↓
订单状态：创建 → 已确认
    ↓
把订单信息写入 Elasticsearch → 骑手端可以搜索到这个订单了
```

**为什么确认后要写 ES？** 因为骑手搜索订单时，需要按地理位置、价格等条件筛选。MySQL 做这种查询很慢，Elasticsearch 是专门为搜索设计的，支持地理距离排序。

### 2. 商家制作完成

```
商家点击"制作完成"
    ↓
订单状态：制作中 → 等待骑手取餐
    ↓
三个动作同时异步执行：
    ├→ 发消息给资金服务 → 把菜品收入打给商家（扣除骑手配送费）
    ├→ 发消息给商家服务 → 增加商家订单数统计
    └→ 发消息给菜品服务 → 增加菜品销量统计
```

**注意**：这三个动作都是通过消息队列异步处理的，不会阻塞用户。这就是"事件驱动"——一个动作触发多个事件，各自独立处理。

### 3. 骑手接单

```
骑手点击"接单"
    ↓
订单状态：等待骑手 → 骑手已接单
    ↓
更新 ES 中的订单状态（标记为"已被接单"，其他骑手就看不到了）
    ↓
发消息给聊天服务 → 自动创建"用户+商家+骑手"三方聊天室
```

**为什么要在接单时创建聊天室？** 因为接单后三方需要沟通：用户可能说"不要辣"，商家可能说"做好了快来取"，骑手可能说"到楼下了"。

### 4. 骑手送达

```
骑手点击"已送达"
    ↓
订单状态：配送中 → 已送达
    ↓
发消息给资金服务 → 配送费打给骑手
```

### 5. 用户确认收货

```
用户点击"确认收货"
    ↓
订单状态：已送达 → 已完成
    ↓
两个动作异步执行：
    ├→ 发消息给用户服务 → 增加用户下单次数统计
    └→ 发消息给聊天服务 → 关闭聊天室（订单完成，不需要再聊天了）
```

### 6. 退款（用户申请退款 / 商家拒绝订单）

```
退款请求
    ↓
检查：这个订单当前状态允许退款吗？
    ├→ 已创建、已确认 → 允许退款
    └→ 其他状态 → 不允许
    ↓
订单状态 → 已退款
    ↓
先更新数据库，再发消息给资金服务 → "退钱"
    ↓
资金服务收到消息 → 把钱从商家账户退还给用户
```

## 订单服务维护了哪些消息队列？

订单服务是一个消息"生产者大户"——它向 RabbitMQ 发送大量消息，驱动其他服务工作：

| 消息队列 | 什么时候发 | 谁来消费 | 干什么 |
|---------|-----------|---------|--------|
| 注册资金订单记录 | 下单时 | 资金服务 | 创建一条扣款记录 |
| 延时回滚死信队列 | 下单时 | 订单服务自己 | 30 分钟后如果还没支付，自动退款 |
| 回滚资金 | 退款/拒绝时 | 资金服务 | 把扣掉的钱退回去 |
| 打款给商家 | 制作完成时 | 资金服务 | 给商家打菜品收入 |
| 打款给骑手 | 配送完成时 | 资金服务 | 给骑手打配送费 |
| 增加商家订单数 | 制作完成时 | 商家服务 | 统计商家接了多少单 |
| 增加菜品销量 | 制作完成时 | 菜品服务 | 统计菜品卖了多少份 |
| 增加用户订单数 | 收货确认时 | 用户服务 | 统计用户下了多少单 |
| 创建聊天室 | 骑手接单时 | 聊天服务 | 创建三方聊天 |
| 关闭聊天室 | 收货确认时 | 聊天服务 | 关闭聊天 |

## 设计中的"聪明之处"

### 1. 延时回滚：30 分钟不付钱自动退款

这是一个很巧妙的设计。下单时，订单服务发了一条消息到"延时队列"，设置了 30 分钟的 TTL（存活时间）。30 分钟后，这条消息还没被消费（说明用户没支付），就会自动进入"死信队列"。订单服务自己的消费者监听死信队列，收到消息后自动退款。

**这样就不需要定时任务去扫描"超时未支付"的订单了**——消息队列帮你做了延时触发。

### 2. 分布式锁防重复下单

同一个用户短时间内发起多个下单请求，只有一个能拿到锁。其他请求直接返回"操作太频繁"。这比在数据库层面做唯一约束更优雅——用户不会看到数据库报错，而是得到一个友好的提示。

### 3. Feign 调用 + MQ 消息的组合使用

这个模块完美展示了什么时候用同步调用、什么时候用异步消息：

- **同步调用（Feign）**：查菜品、算距离、校验优惠券——这些都是下单必须拿到结果才能继续的
- **异步消息（MQ）**：扣钱、加统计、建聊天室——这些都是"通知一下"就行，不需要等结果

## 这个模块的"问题"和"可改进的地方"

### 1. Service 类太大了

`OrderServicerImpl` 这个类承担了太多职责：下单、查询、各种状态变更、退款，全部挤在一个类里。更好的做法是拆分成多个 Service：`OrderCreateService`、`OrderQueryService`、`OrderStateService` 等。

### 2. `@RefreshScope` 和 `@Transactional` 同时使用

`@RefreshScope` 会创建一个代理对象，可能和 `@Transactional` 产生冲突，导致事务失效。正确的做法是把配置读取和业务逻辑分开。

### 3. 没有 Feign 降级

如果菜品服务挂了，下单接口会直接报错。更好的做法是给每个 Feign 客户端配置一个降级兜底类，当下游服务不可用时返回缓存数据或友好提示。

## 如何本地启动？

```bash
# 1. 确保 MySQL、Redis、RabbitMQ、Nacos、Elasticsearch 已启动
# 2. 执行数据库建表脚本
# 3. 在 Nacos 中导入配置
# 4. 启动服务
cd Order
mvn spring-boot:run

# 5. 验证
curl http://localhost:10009/order/simple?start=0&need=10
```

## 学习要点

1. **分布式锁的实战用法**：Redisson 的 tryLock + finally unlock 模式
2. **Feign 声明式调用**：如何定义接口、如何传递参数
3. **RabbitMQ 延时消息**：TTL + 死信队列实现延时触发
4. **Seata 分布式事务**：`@GlobalTransactional` 注解的使用
5. **Elasticsearch 的地理位置搜索**：Spring Data ES 的 Repository 用法
6. **状态机模式**：如何管理复杂的状态流转
