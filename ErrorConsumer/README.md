# ErrorConsumer（异常处理）

> 端口：10030 | 服务名：error-consumer

## 1. 这个模块是干什么的？

ErrorConsumer 是整个 SeekFood 系统里**最"清闲"的模块**——它平时什么都不干，只有在消息队列出问题的时候才登场。

它的工作很简单：**监听 RabbitMQ 死信队列，把处理失败的消息记到日志里**。就这么一件事。

你可能会觉得：就这？但这恰恰是分布式系统里最容易被忽视、又最不可或缺的一环。想象一下，订单服务发了一条 MQ 消息说"扣钱"，结果资金服务的消费者处理失败了，这条消息如果不被任何人知道，钱就永远扣不了了。ErrorConsumer 就是那个"最后知道消息去哪了"的人。

## 2. 什么是死信队列，消息为什么会进死信？

要理解死信队列，先理解正常的消息流程：

```
生产者发消息 -> 交换机 -> 队列 -> 消费者处理 -> 确认(ACK) -> 消息被删除
```

但有时候消费者处理会失败，消息不能直接删掉。RabbitMQ 提供了一个机制：**把处理失败的消息转到一个专门的"死信队列"里**。这就好比快递送不到收件人，不是直接扔掉，而是放到一个"问题件"区域等待处理。

消息变成"死信"有三种情况：

**第一种，消费者明确拒绝。** 消费者收到消息后，发现数据有问题（比如格式不对），调用 `basic.nack` 或者 `basic.reject` 明确拒绝，并且不重新入队。这条消息就会被转发到死信队列。

**第二种，消息过期。** 消息在队列里待了太久（超过了 TTL 存活时间），一直没人消费，到期后自动转入死信。

**第三种，超出重试上限。** 消费者处理失败抛出异常，RabbitMQ 会自动重试。但这个模块在 Nacos 配置里把最大重试次数设成了 3 次（`max-attempts: 3`），重试 3 次还是失败，就不再重试了，消息转入死信。

**那死信队列是怎么配置的？** 每个业务队列在创建时，通过 `x-dead-letter-exchange` 参数指定一个死信交换机。当消息变成死信时，RabbitMQ 自动把它转发到这个死信交换机，再由死信交换机路由到死信队列。这个项目的死信交换机叫 `errorExchange`，死信队列叫 `errorQueue`。

## 3. 这个模块是怎么兜底的？

ErrorConsumer 的工作流程非常简单：

**第一步，监听死信队列。** 通过 `@RabbitListener(queues = "errorQueue")` 注解，Spring 自动从死信队列里拉取消息。

**第二步，读取消息头。** RabbitMQ 在转发死信时，会自动在消息头里塞一些元数据：
- `x-original-exchange`：这条消息原本是从哪个交换机发出的
- `x-original-routingKey`：原本的路由键是什么
- `x-exception-message`：消费者处理失败时的异常信息
- `x-exception-stacktrace`：完整的异常堆栈

**第三步，记录日志。** 把这些信息拼成一条 ERROR 级别的日志，输出到控制台和日志文件。格式大概是：

```
交换机:orderExchange，在投递key:refund时，发生异常:资金不足,
完整异常为:com.seek.food.common.exception.BizException: ...
```

**就这三步，不做任何其他事。** 它不重试、不报警、不补偿——只是记录。为什么不做更多？因为 ErrorConsumer 的职责是"记录现场"，具体怎么处理（比如人工介入、定时补偿、发送告警）应该由其他机制来完成。保持职责单一，代码才简单可靠。

**为什么死信交换机用 Fanout 模式？** Fanout 是广播模式，消息会发给所有绑定的队列。这样将来如果加一个"告警消费者"（比如收到死信就发钉钉通知），只需要新增一个队列绑定到同一个 Fanout 交换机，ErrorConsumer 完全不用改。

## 4. 亮点和坑

**亮点：**

- **职责极简**：只做一件事——记录日志。代码非常短，核心逻辑不超过 20 行，几乎没有 bug 空间。
- **Fanout 广播模式**：为未来扩展（告警、统计、自动补偿）留好了接口，不用改任何现有代码。
- **最小化依赖**：只依赖了 Spring Boot、Nacos 配置、RabbitMQ 和 SkyWalking，没有数据库、没有 Redis、没有 Feign。轻量到极致，启动快、内存占用小。
- **配置驱动**：死信队列的名称、交换机名称全部从 Nacos 读取，改配置不用改代码。

**需要注意的坑：**

- **ErrorConsumer 不处理补偿**：它只记录，不重试。如果业务需要"消息处理失败后自动补偿"，应该在业务模块自己实现本地消息表或定时任务，不能依赖 ErrorConsumer。
- **日志可能会很多**：如果某个业务模块的消费者大面积出问题，ErrorConsumer 的日志会爆炸。需要配合日志监控（比如 ELK）来设置告警阈值，而不是人工盯着日志看。
- **死信队列本身也需要监控**：如果死信队列积压了大量消息，说明系统出了大问题。建议对死信队列的消息数量设置监控告警。

## 5. 快速启动

**需要先装好的东西：**
- JDK 21
- RabbitMQ 3.12+（死信队列就在 RabbitMQ 里）
- Nacos 2.4+（配置中心）

**注意：** ErrorConsumer **不需要** MySQL、Redis 或其他中间件，它只连 RabbitMQ 和 Nacos。

**启动步骤：**
1. 确保 Nacos 里有 `common-default-connection-dev.yaml`（包含 RabbitMQ 连接信息）和 `mq-name-bind-dev.yaml`（包含死信交换机/队列定义）
2. 确保 RabbitMQ 在运行
3. 启动 `ErrorConsumerApplication`，端口 10030

**验证服务：**
启动后，在 RabbitMQ 管理界面（`http://localhost:15672`）里应该能看到 `errorExchange`（Fanout 类型）和 `errorQueue`，并且队列已经绑定了 `ErrorConsumer` 这个消费者。

**模拟测试：**
可以通过 RabbitMQ 管理界面手动往 `errorExchange` 发一条消息，ErrorConsumer 的日志里应该能看到相应的 ERROR 日志输出。

**依赖的模块：** 只依赖 DTO 和 Util（基础依赖），不依赖 Config 模块（配置通过 Nacos 直接读取，不需要 @Import 注解）。
