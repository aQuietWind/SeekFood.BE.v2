# Meal（菜品服务）

> 端口 **10004** | 服务名 **meal** | 数据库 **seek_food_meal**

---

## 1. 这个模块是干什么的？

Meal 服务负责整个 SeekFood 平台里**菜品**相关的所有操作。商家可以在这里新增菜品、修改价格、上传图片、上架下架，用户则可以看到菜品列表和详情。

简单来说，它就是"菜单管理系统"——只不过这个系统是微服务中的一个独立模块，其他服务（比如订单服务、商家服务）会通过远程调用或消息队列跟它打交道。

---

## 2. 菜品上架流程

假设你是商家，刚做好了一道新菜，想在平台上线，整个流程大概是这样的：

**先做参数校验。** 菜品名称、价格、内容描述这些字段都会经过严格的格式检查。比如名称不能太长或太短，价格不能是负数，这些规则都动态配置在 Nacos 里，随时可以改，不需要重启服务。

**再检查冷却期。** 这里有个关键设计：每个操作（新增、修改价格、删除等）都有独立的冷却时间。什么意思呢？就是你不能在 5 秒内连续新增两道菜，也不能在 10 秒内连续改价格。这是用 Redis 的 `setIfAbsent` 实现的，本质上是一个轻量级的分布式频率限制器，防止恶意刷接口。

**最后写入数据库。** 菜品 ID 不是数据库自增的，而是用 Redis 维护的计数器来生成，保证分布式环境下 ID 不冲突。这个设计让 ID 生成独立于数据库，后面做分库分表时会更方便。

后续的修改价格、更新图片、删除菜品等操作，流程都类似：校验参数 -> 检查冷却期 -> 操作数据库 -> 清理缓存。

## 3. 缓存策略

菜品详情是高频读取数据，如果每次都查数据库，MySQL 迟早扛不住。所以 Meal 服务用了三层缓存架构：

**第一层：JVM 本地缓存（Caffeine）。** 这是最快的，数据就在内存里。Meal 服务启动时会创建一个 Caffeine 缓存实例，设置最大条数和过期时间，写后 30 分钟自动过期。

**第二层：Redis 分布式缓存。** 如果 Caffeine 没命中，就查 Redis。Redis 里存的是 JSON 序列化的菜品对象，命中后反序列化回来，同时顺手写回 Caffeine，这样下次请求就直接走 JVM 了。

**第三层：MySQL 数据库。** 如果 Redis 也没有，那就去数据库查。查出来之后，先序列化写入 Redis，再写入 Caffeine，下次请求就能命中缓存了。

特别注意：当数据更新时，会**同时删除 Redis 和 Caffeine 两层缓存**，而不是更新缓存。这叫"删除缓存"策略，能避免并发写导致的数据不一致问题。另外，如果查出来的结果是 null（比如菜品不存在），也会缓存一个特殊标记 `"n"` 到 Redis，防止别人用不存在的 ID 反复冲击数据库——这就是经典的缓存穿透防护。

## 4. 销量统计怎么做的？

销量统计不是 Meal 服务自己算的，而是**订单服务通过消息队列异步通知**的。

订单服务在下单成功后，会发一条 MQ 消息到 Meal 服务，消息里带着"菜品 ID"和"销量变化量"。Meal 的 `ChangeMealSalesVolumeConsumer` 收到消息后，直接执行一条 SQL：`update meal set meal_sales_volume = meal_sales_volume + ? where meal_id = ?`。

这样做的好处是：**解耦**。订单服务不需要知道 Meal 服务的存在，只需要发消息就行。而且销量统计不会阻塞下单流程，即使 Meal 服务暂时挂了，消息也会在队列里等着，等它恢复后继续消费。

## 5. 亮点和坑

**亮点：**

- **多级缓存 + 防穿透**：Caffeine -> Redis -> MySQL 三级缓存，查询性能拉满，同时用 Redis 空值标记防止缓存穿透。
- **冷却期设计**：每个操作都有独立的频率限制，不是粗暴的全局限流，而是针对用户+操作维度的精细化控制。
- **文件异步删除**：更新菜品图片时，新图先存，数据库更新成功后再通过 MQ 延时删除旧图。如果数据库更新失败，新图也会被 MQ 删除。MQ 发了延时消息（TTL），到期后进入死信队列，死信消费者再尝试删除，保证旧文件不会永久残留。
- **定时清理兜底**：如果 MQ 删除文件失败了，文件路径会被写入 Redis Stream，由 `OldFileClearScheduled` 定时任务每 5 秒轮询一次，重试删除。这是最后一层保障。
- **ID 用 Redis 计数器生成**：不依赖数据库自增，适合分布式场景。

**坑：**

- 缓存和数据库可能存在**短暂不一致**，因为先删缓存再写数据库，或者先写数据库再删缓存，中间都可能被其他请求读到旧数据。这个服务的策略是"先更新数据库，再删除缓存"，短暂不一致可以接受。
- 冷却期用 Redis 的 `setIfAbsent` 实现，如果 Redis 挂了，所有操作都会被拒绝，需要有降级方案。
- 文件删除链路比较长（MQ -> 死信 -> Stream -> 定时任务），排查问题时需要顺着链路一步步看。

## 6. 快速启动

### 环境要求

- JDK 21+
- Maven 3.9+
- MySQL（需要先执行 `src/main/resources/MysqlCreate.sql` 建库建表）
- Redis（缓存、冷却期、ID 计数器）
- RabbitMQ（销量更新、文件删除）
- Nacos（服务注册发现 + 配置管理）

### 启动步骤

1. 建库：执行 `MysqlCreate.sql`。
2. 确认 Nacos 中已配置好 `COMMON_GROUP` 和 `MQ_GROUP` 和 `SEEK_FOOD_GROUP` 的相关配置文件。
3. 启动 Redis 和 RabbitMQ。
4. 运行 `MealApplication.java` 主类，端口 10004。

### 核心接口一览

| 接口 | 方法 | 说明 |
|------|------|------|
| `/meal/insert` | POST | 新增菜品 |
| `/meal/getSimple` | GET | 获取菜品预览列表（分页） |
| `/meal/getSimpleByType` | GET | 按类型获取菜品预览 |
| `/meal/getDetail` | GET | 获取菜品详情（走缓存） |
| `/meal/updateMessage` | PUT | 修改菜品信息 |
| `/meal/updateShowImage` | PUT | 修改菜品图片 |
| `/meal/updatePrice` | PUT | 修改价格 |
| `/meal/updateSell` | PUT | 上架/下架 |
| `/meal/delete` | DELETE | 删除菜品 |

### 依赖关系

本模块依赖 **Config**（Nacos 配置）、**Util**（工具类）、**DTO**（数据传输对象）三个公共模块，不直接依赖其他业务模块。
